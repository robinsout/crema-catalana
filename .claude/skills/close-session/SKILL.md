# Закрытие сессии

Цель: следующая сессия начинается с чистого листа — всё закоммичено, проверено, задеплоено, а в памяти записано, где остановились и что дальше. Механические проверки делает `npm run session` (`scripts/session-check.ts`, только читает и сообщает), остальное — ты.

Работай по шагам. Если что-то упало и починить быстро нельзя — не пушь, а честно опиши в итоге, что сломано.

**Только нужные шаги.** Объём работы определяют изменения (незакоммиченные файлы + незапушенные коммиты), а не привычка:
- **ничего не изменилось** → шаги 4–5 пропустить целиком: код уже проверили хук `pre-push` и CI. Один лёгкий `npm run session` (он сам не гоняет тесты), память, итог.
- **только документация** (`*.md`, `.claude/`) → коммит и пуш без тестов: скрипт, хук и CI их пропускают сами; ждать CI не нужно — он не запускается.
- **код или контент** → полный цикл. Скриншоты — только если затронут вид (скрипт решает сам), озвучка — только если менялись тексты уроков, деплой сервера — только если менялись `server/`, `shared/`, `deploy/`.
Не запускай проверки «на всякий случай» сверх плана скрипта; `--full` — только по просьбе пользователя или при подозрении, что что-то сломалось вне изменений.

## 1. Остановить своё фоновое
Останови свои фоновые задачи и мониторы этой сессии (TaskStop). Временные файлы — только в scratchpad; если что-то временное попало в проект (пробные спеки в `e2e/`, `.mjs`-скрипты в корне), удали.

## 2. Разобрать изменения
`git status` и `git diff`. Для каждого изменения пойми, откуда оно:
- твоё из этой сессии — коммитишь;
- непонятное (пользователь правил руками, другой инструмент) — спроси, прежде чем коммитить или откатывать. Ничего не откатывай сам.
Никогда не коммить секреты, `.env`, ключи, коды синхронизации, файлы из `~/.claude`.

Что ещё нужно, скажет раздел «Что изменилось» в `npm run session`:
- «Тексты уроков» → `npm run audio` (нужен edge-tts) до коммита;
- скриншоты скрипт гоняет сам, когда затронут вид; отличия показать пользователю, эталоны обновлять (`npm run e2e:visual:update`) только если изменение намеренное;
- «Код сервера синхронизации» → после пуша `npm run deploy:sync` (с согласия пользователя: на сервере живёт и его бот).

## 3. Бэклог и документация
- `BACKLOG.md`: статусы того, что сделано в сессии (✅ / 🚧 с пометкой шага), новые идеи — новыми пунктами.
- `CLAUDE.md`: только если появились новые правила, команды или договорённости, которые нужны будущим сессиям.
- `deploy/README.md`: если менялись сервер, безопасность или деплой.

## 4. Проверить и закоммитить
1. `npm run session` — проверки по плану. До коммита ожидаемо одно ✗ «Незакоммиченные изменения»; любые другие ✗ — чинить сейчас.
2. Коммиты — по смыслу (урок отдельно от фичи, фича отдельно от правок документации), сообщения на английском в стиле истории (`git log --oneline -15`), с co-author строкой из системных инструкций. Автор — личный адрес (проверяет скрипт).
3. `git push` — хук `pre-push` гоняет `npm run check` и e2e, если пушится не только документация. Не обходить хуки (`--no-verify`), не делать force push. Если в сессии есть и код, и документация, порядок не важен: хук смотрит на все отправляемые коммиты сразу.

## 5. Дождаться деплоя
Только если пушился код или контент (на документацию CI не запускается). Подожди CI ограниченным циклом (не дольше ~15 минут, интервал 30–60 с: GitHub API без входа даёт 60 запросов в час), например фоновой командой, которая сама завершится. Затем `npm run session` (после пуша изменений нет, тесты он не запустит): должно быть «Всё в порядке» или только понятные предупреждения (открытые PR Dependabot, сертификат, перезагрузка сервера). Упавший CI — открыть ссылку из отчёта, разобраться, починить или записать в итог.

## 6. Обновить память
Папка памяти проекта: `~/.claude/projects/-Users-vk-Pet-projects-catala/memory/`.
- `session-state.md` — **обязательно**: дата (абсолютная), что сделано за сессию (коротко, с коммитами), что открыто, следующие шаги, решения, которых ждём от пользователя. Это первое, что читает следующая сессия; заменяй устаревшее, а не дописывай бесконечно.
- Другие заметки — если поменялись факты (сервер, аудит, правила работы, предпочтения пользователя). Новое правило от пользователя — отдельная заметка `feedback` с **Why** и **How to apply**.
- Не записывать то, что уже есть в репозитории (код, история git, CLAUDE.md, BACKLOG.md).
- `MEMORY.md` — одна строка на заметку. После правок `npm run session -- --offline` проверит индекс (тестов не будет: память вне репозитория).

## 7. Итог пользователю
Коротко, по-русски:
- что сделано за сессию и что закоммичено (хеши);
- состояние: тесты, CI, сайт, сервер — из последнего `npm run session`;
- что не сделано или сломано, если есть;
- вопросы, ждущие решения пользователя;
- с чего начать в следующий раз.
